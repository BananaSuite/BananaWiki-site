A chat for your group, on models you choose

Run a chat for your group on your own server, using local Ollama models or external providers such as Anthropic, OpenAI and OpenRouter. Administrators decide who can use which model, and how much.

Features

One installation serves a group, such as a class, a lab or an office. Everyone has their own account, and administrators decide which models each person can use, and how much.

Chat

  • Streaming answers, with the model’s reasoning when available
  • Markdown and code rendering, with copy and download on every code block
  • Attachments, including images, PDFs, text and code files
  • Search, exports, share links and chats kept out of your history
  • Hosted models work when the local model server is down

Personalities

  • An avatar, a greeting, conversation starters, a preferred model and a response style
  • A default personality for new chats, and templates to start from
  • Share links, and import and export as JSON
  • Featured personalities published for everyone, with moderation

API

  • An OpenAI-compatible API: chat completions, the model list and image generation
  • Personal API keys, read-only or with full access and an optional expiry, and a playground
  • An account’s keys share its allowance and request-rate rules

Cloud sessions (optional)

  • Coding sessions with a tool-capable model in an isolated sandbox
  • Tool calls and command output as they happen, and the files the model changes
  • Download the workspace or a Git patch, or send a follow-up while the workspace is retained
  • Off by default, and administrators choose who can start one. Model access, token, time and resource limits apply

Administration

  • Users and invitations, and two-step verification for every account, which can be required for administrators
  • External API providers with keys encrypted on the server, a connection test and models picked from the provider’s own list
  • Presets for Anthropic, OpenAI, OpenRouter, Google Gemini, Mistral and other OpenAI-compatible services, and for local servers such as LM Studio, vLLM, llama.cpp and LiteLLM (each provider’s billing and terms apply)
  • Pools of Claude Code and Codex subscription accounts, with usage caps and strict model limits (optional, and shared use needs the provider’s approval)
  • Access rules per model and category, token allowances per 5 hours, optional weekly limits and request-rate rules
  • Metrics, an audit log, maintenance mode and theming

Running it

  • One command installs, updates, backs up and restores a server, and the generated HTTPS proxy configuration also works behind Cloudflare
  • Updates follow release tags with dependencies pinned by hash. They take a backup first and roll back if the new version doesn’t start
  • Backups, optionally encrypted and authenticated in a private Git repository
  • Separate web and GPU servers, volunteer worker PCs and image generation with ComfyUI
  • Light and dark themes and reading settings for each person, under Appearance in the account menu

Install

Try it on your own computer first. For a group, the usual setup is two machines: a GPU server that runs the models and a web server that holds accounts and chats.

On your computer

# Python 3.12 or newer, and Ollama with one model
ollama pull qwen3:4b
git clone https://github.com/BananaSuite/BananaChat.git
cd BananaChat
./dev.sh

Then open http://127.0.0.1:8000. The terminal prints the token you need to create the first administrator, and the server only listens on your own computer.

On two Linux servers

# on both servers, check out the latest release
git clone https://github.com/BananaSuite/BananaChat.git
cd BananaChat
git checkout "$(git tag --list 'v*' --sort=-v:refname | head -n 1)"

# on the GPU server (this prints a pairing code)
sudo ./banana install --mode compute --domain compute.example.org
sudo bananachat proxy --install

# on the web server
sudo ./banana install --domain chat.example.org --pair
sudo bananachat proxy --install

Check out the same release on both servers, and keep the pairing code secret. To put everything on one machine, use --mode single. To keep an Ollama server that’s already running, use --ollama-url. The deployment guide and the backups guide cover the rest.

Where conversations go

Where are chats stored?

Chats are stored in the server’s SQLite database. Local Ollama models run on your own hardware, while a cloud provider you configure receives the requests and applies its own privacy terms.

Where do cloud sessions run?

Tools run in an isolated workspace on the sandbox runner the administrator configured. Instructions, file content and tool results can be sent to the chosen model provider, and administrators can review the session logs. Workspaces expire after the retention period the administrator sets, so download the files you want to keep.

Which models support cloud sessions?

Models that support tool calling, through Ollama or an external API provider. Cloud sessions stay off until an administrator configures the runner and turns them on.

Are chats kept out of history private?

They don’t appear in your history and are deleted after a time the administrator sets. Administrators can still review them in an audit log, and the interface tells you so.

Who can read prompts when worker PCs are used?

The people running those worker PCs can read the messages, conversation context and images sent to their machines. Worker PCs are off until an administrator adds them.

What does a share link expose?

Anyone who has the link can read the shared conversation.

How it relates to BananaWiki

BananaChat started as BananaAI, a way to run AI models on your own hardware. It began as part of BananaWiki and was later split out into its own application.

The two are separate programs with their own installations and accounts, and BananaWiki doesn’t include a language model. Luca Zani created both and maintains them with contributors. The About page tells the full story.
